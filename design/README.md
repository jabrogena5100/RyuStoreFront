# Design

How the storefront is designed and where to look. The brief is [BRIEF.md](BRIEF.md); the tokens are the single source of truth in
[`web/src/styles/tokens.css`](../web/src/styles/tokens.css); the living reference is the `/design` page of the running app.

## What is here

| Path | What |
| --- | --- |
| `BRIEF.md` | Audience, brand, colour, type, motion, responsiveness, stack, checklist. Decisions and their reasons. |
| `screens/*.png` | Full-page screenshots of every screen built so far, at desktop (1440 px) and phone (390 px) width, Chromium. Generated by the script below, not hand-made. |
| `screens/AXE.txt` | One line per page from the accessibility scan (axe, WCAG 2.0/2.1 A and AA). |

## Regenerate (one command, needs only Docker)

```
scripts/design-shots.sh
```

It rebuilds the frontend, serves it, takes the screenshots and runs the scan. Frontend tooling alone: `scripts/web.sh npm run build`, `scripts/web.sh npx tsc --noEmit`.

| --- | --- | --- |

**Not built yet** (from the brief): checkout, order confirmation, order history, admin product edit, admin orders. They come after the screens above are signed off.

The `?state=` URLs exist only so each state can be shown and screenshotted; they go away when the pages are wired to the real API.

## Known limits (not hidden)

- The images are placeholders by design (typographic, one 4:5 ratio). No real product photography exists yet.
- Reviewed by the screenshots only: no real device, no Firefox or WebKit run yet, no keyboard-only or screen-reader walkthrough, no Lighthouse numbers. The axe scan catches only the automatable part of WCAG.
- Prices, products and sizes are fixtures that mirror the API's response shapes and the backend seed vocabulary; nothing calls the API yet.
